# Аудит продуктивності сервера PartsON і план покращень

Перевірено production `https://partson.shop` 20 листопада 2026 року. Прогріті маршрути витримали короткий тест до 5 HTTP-запитів за секунду без помилок. Основні проблеми: майже заповнений диск, активний обмін зі swap, повільні та нестабільні звернення до 1С, HTTP 500 на окремій моделі авто і блокування основного потоку мобільного каталогу. Головна та перевірена картка товару мають добрі лабораторні показники.

Пріоритет робіт: звільнити запас диска, перевірити стабільність поточних лімітів пам’яті, випустити вже підготовлений спільний ліміт звернень до 1С, відновити проблемні сторінки моделей, потім оптимізувати каталог. Зміни production-конфігурації, очищення, деплой і перезапуски під час цього аудиту не виконувалися.

## Обсяг і методика

- Активний реліз під час основних вимірювань: `/var/www/Partson-release-20261119-80f970f`, Git `80f970f524c599a87844e6d0a05cb3126bdb751d`, build ID `A_2EJsVcpjRyvD5YO8jMa`. Next.js 16.4.6, React 19.2.8. Локальна робоча копія під час аудиту оновлювалася; її код не прирівнюється до активної збірки.
- SSH-діагностика: PM2, `/proc`, `df`, `free`, `vmstat`, PSI, nginx, Apache і журнали. 100 знімків ресурсів протягом приблизно 203 секунд, 08:33:28–08:36:51 за Києвом. Це спільне навантаження сервера: сайт, фонові процеси та аудиторські запити.
- HTTP: по 5 послідовних запитів до 12 маршрутів; gzip/br і keep-alive. Окремо перевірено вміст публічного каталогу, ціни 16 товарів і живе оновлення. POST використовувався лише на маршрутах читання даних.
- Навантаження: змішані запити до головної, каталогу, груп, товару, API каталогу та пошуку. Етапи 1, 3 і 5 запитів/с, по 20 секунд, максимум 5 одночасних запитів. Передбачена зупинка при помилці або відповіді понад 5 секунд. Усі три етапи завершилися.
- Lighthouse 13.6.0: мобільні головна, каталог, товар; головна з desktop preset; повторний мобільний каталог. Використано стандартну симуляцію Lighthouse, новий браузерний профіль. Chrome 157. Це лабораторні дані; INP реальних покупців і польові перцентилі не вимірювалися.
- Playwright і Chrome DevTools Protocol: 390×844 та 1440×900, мережеві запити, скриншоти, помилки. Для мобільного проходу CPU ×4, затримка 150 мс, 1,6 Мбіт/с завантаження. Перший прохід з інструментуванням coverage використано лише для мережевої діагностики: збір підсумку coverage мав помилку інструмента, а CPU-витрати збільшувало саме профілювання. Контрольний мобільний каталог без coverage завершився успішно; оцінки блокування взято з Lighthouse.
- Проаналізовано останні 12 000 рядків nginx з фільтром доменів `partson.shop` і `www.partson.shop`: 11 544 записи за 00:28:36–08:39:39. Вибірка включає ботів та аудит. `request_time` охоплює передавання відповіді клієнту, тому це не ізольований час виконання backend.

Кеші не очищалися. Перший запит у вибірці не означає гарантовано холодний кеш. Межа пропускної здатності, тривалий тест, авторизовані сценарії та оформлення замовлень цим аудитом не встановлюються.

О 09:01 за Києвом фінальна зовнішня перевірка дала HTTP 200: головна — 602 мс повного запиту, каталог — 646 мс. Повторний SSH до порту 22 завершився таймаутом; причину недоступності адміністративного доступу не встановлено. Останній успішний знімок PM2 зберігається окремо; стабільність процесу після нього не підтверджена через SSH. Перед роботами на сервері потрібно відновити й перевірити цей доступ.

У початковій вибірці журналу за сьогодні було 234 рядки з таймаутами та 24 згадки `AutoModelBreakdownUnavailableError`. Це кількість записів, а не точна кількість невдалих запитів: повідомлення про 1С агрегуються.

Мобільний каталог відтворювано має високий TBT. У першому звіті: 4,5 с роботи основного потоку, з них 1,14 с виконання скриптів, 0,74 с стилів і layout; найбільше завдання — близько 1,11 с у моделі Lighthouse. LCP каталогу в Lighthouse — текст банера згоди на аналітику. Тому 1,2 с не означає, що фото, актуальна ціна та керування покупкою готові за 1,2 с. Потрібні окремі позначки готовності першої картки та її дій. Розбіжність Speed Index між двома проходами також показує, чому один score не замінює вимірювання. [Як Lighthouse рахує оцінку](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring).

Виявлені додаткові витрати:

- Загальний `site.11374302ea.css`: 1 088 249 байтів після розпакування, близько 168 KB стисненого тіла. Критичний CSS каталогу додає близько 57 KB. Lighthouse оцінює невикористану в сценарії частину CSS каталогу приблизно у 114 KiB. Це оцінка для початкового стану; видаляти всі такі правила автоматично не можна.
- У першому mobile-каталозі за вікно спостереження було 17 API-відповідей, зокрема 12 звернень до пакетних зображень, 2 до сторінок і 3 до цін. Код уже має prefetch двох наступних сторінок. Слід зіставити тіла запитів, видимі картки та prefetch перед висновком про дублювання.
- На товарі й у desktop-каталозі також завантажувалися критичні стилі інших маршрутів. Ймовірний напрям перевірки — випереджальне завантаження навігації; це не доказ, що стилі всіх цих маршрутів потрібні для першого екрана.
- У звіті каталогу присутній Google tag приблизно 209 KB; Lighthouse оцінює невикористану частину близько 102 KB. Треба окремо порівняти початковий стан, відмову та надану згоду. Приписувати весь TBT аналітиці за цим виміром не можна.
- У шести браузерних сценаріях не зафіксовано JavaScript `pageerror` або горизонтального переповнення; зафіксований HTTP 503 живого оновлення описано вище. Це не повний аудит доступності інтерфейсу.

Винести збірку на окрему машину/CI, переносити готовий перевірений артефакт | DevOps, 1 день | PM2 контролює саме auth; реліз не відбирає пам’ять у live-сервера; перемикання й відкат відтворювані |
| 12 | P2, за результатами доби | Розглянути 4 GiB RAM як наступний розмір VPS і збільшення диска; за подальшої конкуренції ресурсів — відокремити 1С від Next.js. Розмір підтвердити повторним тестом | DevOps, 0,5–1 дня плюс перенесення | Під цільовим навантаженням є ≥25% запасу RAM, немає тривалого swap I/O, диск має запас; цифри підтверджені, а не виведені з назви тарифу |

### Важливі умови реалізації

**Диск.** Для активного релізу підтверджено приблизно 660 MiB route-cache, 933 MiB `.cache` і cron очищення route-cache кожні 15 хвилин із ціллю 600 MiB. Отже, встановлювати такий cron повторно не потрібно. Треба перевірити його виконання, сумарні бюджети та старі релізи. Рекурсивна інвентаризація всього диска була обмежена часом; остаточний обсяг безпечного очищення ще треба визначити. Базу 1С та резервні копії не включати в автоматичне видалення.

**Пам’ять і 1С.** Не збільшувати кількість Apache workers або процесів Next.js лише заради паралельності на поточних 2 GiB. Перевірений локальний gate — крок для наступного релізу, не доказ, що він уже усуває таймаути production. Для кількох процесів ліміт на `globalThis` буде окремим у кожному; потрібен загальний бюджет усіх клієнтів 1С. Операції залишків і замовлень мають окремі вимоги й потребують регресійної перевірки.

**Кешування.** nginx уже віддає static напряму та має кеші фотографій із lock і stale background update. Зберегти ці налаштування. Якщо додавати CDN або кеш HTML, перевіряти `Vary` для RSC, cookies, авторизацію та інвалідацію. Приватні партнерські й адміністративні дані не повинні потрапляти до публічного кешу. [Рекомендації Next.js для власного хостингу](https://nextjs.org/docs/app/guides/self-hosting), [правила proxy cache nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html).

**Спостереження.** Sentry встановлено, але DSN не задано ні в перевіреному PM2 environment, ні в `.env.local` активного релізу. Доступні варіанти — активувати наявну інтеграцію або обрати інше сховище метрик і помилок. Потрібні окремі метрики готовності картки та польові LCP/INP/CLS. Для Core Web Vitals цільові p75: LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1; TBT Lighthouse не є виміряним INP. [Web Vitals](https://web.dev/articles/vitals).

## Порядок виконання та перевірка результату

1. **Перший день:** запас диска, збереження шляху відкату, метрики й контроль уже застосованої пам’яті. Не запускати нову production-збірку, доки не перевірений запас для її артефактів.
2. **Наступні 1–3 дні:** перевірити локальний gate і випустити його окремим релізом; відновити breakdown проблемних моделей; перевірити читання, ціни, живі залишки та відсутність негативного кешування.
3. **Далі 2–4 дні:** каталог, prefetch, CSS і підтверджені бюджети кешів. Вимірювати кожен пакет змін окремо, щоб зберегти причинний зв’язок із результатом.
4. **Після цього:** повторити ті самі HTTP- та Lighthouse-сценарії. На staging із реалістичними даними провести 30–60 хвилин сталого навантаження, окремо нові пошуки, нові сторінки, прострочені кеші, збій 1С і відновлення. Збільшувати інтенсивність ступенями; для production залишати погоджений робочий бюджет.
5. **За 24–72 години production:** оцінити рестарти, swap I/O, 5xx, p95 API та вартість фонових завдань. Якщо ресурси залишаються вузьким місцем, переходити до розширення VPS або розділення служб.

Пропоновані робочі бюджети: p95 прогрітих HTTP-маршрутів ≤500 мс; p95 живого оновлення ≤1500 мс; 5xx <0,1% за добу; 0 memory restart; диск <80%. Це критерії наступних змін, а не вже досягнуті показники. Алерти: диск >85% warning / >90% critical; RAM available <300 MiB понад 5 хвилин; RSS Next.js >750 MiB понад 5 хвилин; 5xx >1% за 5 хвилин за достатньої кількості запитів; будь-який OOM або новий memory restart. Для маловідвідуваних сторінок додати регулярні синтетичні перевірки.

Для приймання потрібні також коректні дані: 16 товарів у першій відповіді, справжні ціни й фото, правильна пагінація, відновлення після тимчасового збою та ізоляція гостьових, партнерських і адміністративних відповідей. Операції замовлення перевіряти на тестовому середовищі.

Кожен реліз зберігати як готовий артефакт із build ID та переліком змін. Після перемикання перевірити головну, каталог, товар, проблемну модель, static assets і API. У разі регресії повернути попередній артефакт і відповідні шляхи nginx/cron; доступність auth перевірити окремо. Результати першого прогрітого запиту та стабільного кешу записувати окремо.
